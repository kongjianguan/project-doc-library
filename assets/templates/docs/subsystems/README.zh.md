## 每个子系统一页

当一个子系统拥有独立术语、边界、生命周期、扩展点或故障模式时，为它创建页面。使用稳定名称，在上面的表格中登记，并从 `docs/architecture.md` 链接到该页面。

每个页面应回答以下问题：

```markdown
# <Subsystem>

## Purpose

说明职责和边界。

## Ownership and dependencies

说明边界的负责人以及可以调用的依赖。

## Core concepts

定义读者必须共享的类型、状态和不变量。

## API and extension points

描述受支持的入口和扩展规则。

## Failure behavior

描述错误、恢复方式和可观察诊断。

## Verification

列出能够证明契约的聚焦测试、命令或生成检查。
```

## 与源码等价的事实

类型签名、公开选项、生成的 API 区域以及其他来自源码的事实必须有源码归属。链接到生成的参考文档，或从源码声明重新生成。不要在普通 prose 中手工维护第二份签名目录。

## 边界

明确描述依赖方向和所有权。子系统页面可以链接到 Agent Note 了解理由，但当前契约属于此处或它所描述的源码。

## 审查标准

页面应足够精确，能够被验证；也应足够短，便于扫描。如果页面包含多个不相关的边界或读者群体，就拆分页面。新增、删除或重命名子系统后更新架构地图。
